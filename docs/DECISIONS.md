### Why / alternatives / boundaries

- **House Helper umbrella vs separate apps:** favors reuse of auth, safe diagnostics and shared core while keeping each domain's rules and data distinct. Building several independent agents/apps now was rejected as unnecessary complexity.
- **Explicit domain selection vs automatic switching:** keeps user control, predictability and clear topic boundaries; automatic guess-based transitions are not approved.
- **Soft redirection vs blanket refusals:** preserves a natural conversation without turning Kitchen Helper into a general-purpose chatbot. The current release is still about cooking.
- **n8n as optional notifications vs n8n in the critical path:** keeps cooking functionality and local diagnostic evidence available even if automation is offline; no recipes, transcripts, credentials, magic links, or personal data in n8n diagnostic payloads.
- **Visual palette:** user confirmed family of colors only; sample HEX codes in chat were illustrative, not design-system tokens.

### Implementation boundary

Do **not** modify the accepted R3B-3 Admin Bootstrap code or its audit to implement these decisions. Design the Kitchen Web UI and its error correlation in a later scoped increment; implement n8n notifications only after local structured error reporting exists and its privacy/safety boundaries are verified. Future Garden/Vegetable Garden/Home features need their own product criteria before implementation.

## Accepted retention direction — R4C-D2 (2026-10-23)

These decisions record the retention approach the owner ACCEPTED with R4C-D2 (final independent Codex PASS, owner ACCEPT; code RELEASED as `489ff30`). They describe **released code that is not installed, not scheduled and not deployed; no real database has been processed**, and none of them is evidence that any real data has been cleaned. *[State at the release. Updated 2026-10-24: the timer is now installed and active on the technical deployment; its first scheduled run is not yet verified, and no real data is claimed cleaned.]* *[Updated 2026-10-25: the first scheduled run was verified and accepted; it found no expired record and deleted nothing, so still no real data is claimed cleaned.]* They implement KHD-04 and add no product decision. The command and procedures live in `deploy/RUNBOOK.md` (section 14); the gates are in `STATUS.md`.

| ID | Decision | Status |
|---|---|---|
| **KHD-30** | Retention is enforced by physical SQL deletion, row by row. A message or turn request is deleted 365 × 24 hours after its own creation; a sign-in artifact (session, OIDC state, emailed sign-in link, Telegram invitation) at its own `expires_at`, used or not; a conversation only when it is empty and idle for 365 days. `users`, allowlist entries and identity links are never touched, and the cleanup names its tables one by one so that future favourites and long-term preferences (KHD-05) are not deleted with the history they came from. (Implements KHD-04.) | ACCEPTED — R4C-D2; code RELEASED, scheduled on no host *[Updated 2026-10-24: timer installed on the technical deployment; first scheduled run not yet verified]* *[Updated 2026-10-25: first scheduled run verified and accepted]* |
| **KHD-31** | One explicit operator command, `purge-expired`: it deletes by default, `--dry-run` is the explicit preview (a snapshot, not a promise), and it has no option for a date, an age or a table. It runs beside the web service under the shared maintenance lock. No scheduler runs inside the application; scheduling is an opt-in systemd timer on the host, installed only on the owner's approval. | ACCEPTED — R4C-D2; command and units RELEASED, nothing installed *[Updated 2026-10-24: the units are installed on the technical deployment and the timer is active; first scheduled run not yet verified]* *[Updated 2026-10-25: first scheduled run verified and accepted]* |
| **KHD-32** | Deletion is logical, not forensic erasure. The cleanup does not `VACUUM` or checkpoint the database; a deleted row survives in every older backup, so until the backup retention, off-host copy and encryption are decided the 365-day promise holds for the live database only. R4C-D2 invents no backup policy. | ACCEPTED — R4C-D2; backup policy UNDECIDED, a BLOCKER before real data |

### Why / alternatives / boundaries

- **Delete by default vs a dry-run default:** a scheduled run that only counts would delete nothing, so the dry-run default was dropped; the explicit flag is the way to look.
- **No date or scope option:** a mistyped date would delete a year of history.
- **Host timer vs scheduler inside the application:** keeps the web process free of background work and the schedule an operator-visible, disable-able fact on the host.
- **D1 left unchanged:** `upgrade.sh`, `compose.yaml` and `dbtool.py` are D1's. A cleanup holding the shared lock can make `upgrade.sh` report a failed migration that never started; the documented precaution is to stop the timer around an upgrade or a restore. Making the script tell a refused migration from a failed one is **not decided** and left to a later owner decision.
- **Not decided here:** the backup destination, frequency, retention and encryption; where a failed cleanup run is reported; `VACUUM` or checkpointing as a later, separately tested step; what the users are told about retention.

## Accepted product direction — History & Favorites (2026-10-27)

| ID | Decision | Status |
|---|---|---|
| **KHD-34** | (1) A conversation's title is **derived on reading** from its first unexpired user message (60 code points, then "…"); no title is stored, so the title expires with its message and retention (KHD-30) is unchanged. (2) Favorites are **independent of conversation retention**: a favorite is a copy of the answer, with no foreign key to the history and no expiry, and `purge-expired` does not know the table. ### Why / alternatives / boundaries

- **Derived, not stored, titles:** a stored title would be a second copy of conversation text that the purge would have to know about; deriving it on reading keeps the 365-day promise exactly as it was.

The cost is that the promise "everything is deleted after a year" no longer covers it; what the users are told about retention has to say so (`deploy/RUNBOOK.md` 14.7), and a saved recipe is in every backup taken after the upgrade.
- **The limit of 100:** everything else expires, favorites do not, so they need their own bound.
- **Not decided here:** the upgrade of the production database (an owner-approved step under `deploy/RUNBOOK.md` section 9, see 9.1); automatic extraction of preferences, search, renaming and folders for favorites; what the users are told about retention.

| **KHD-38** | **Telegram delivery rules after the independent reviews (2026-10-28, two rounds).** (1) *A duplicate delivery is not a duplicate generation.* An update that Telegram delivers again does not run the assistant a second time once an attempt at it has begun. By what the first delivery left in the database under the key `tg-<update id>`: a **completed** turn is replayed (the answer may reach the chat twice); an attempt that is **still running** (its 90-second lease is live) answers the repeat with the fixed "still preparing" notice (`STILL_BUSY`) and nothing new is started; a **failed or expired** attempt (failure, timeout, lease run out, restart) is not retried and gets a fixed notice to write the message anew; the page's own "send again" still runs a failed message again. The record is the committed claim of the turn (`attempt_count > 0`). An update that **never reached a claim** (dropped before it, or acknowledged and lost with the process) left no record and is handled as a new message. (2) *An update id belongs to the bot, not to the account's current owner (second round).* It is looked up across owners, before anything is fetched and again inside the claim's transaction, with the account's link held (a share lock on the link row on PostgreSQL, reasoned and not run here; the writer lock on SQLite): an update that was admitted for another user is **dropped** with a fixed "the connection changed" notice, in every state of the first attempt (completed, failed, in flight), and nothing of its text, photo or answer is read, stored, sent to the assistant or sent to the new owner; the first owner's rows are untouched. **No migration and no new table:** the turn request that the claim writes already is the record, and the owner of its conversation is the owner of the update. The website refuses idempotency keys that start with `tg-` (400), so a key made up on the page cannot stand for somebody's update. (3) *The tie is checked again where it matters:* when a queued message's turn comes, inside the claim, and under a per-chat binding lock immediately before an answer or a copy is sent. Unlinking takes that lock, removes a link only with a statement that names its account, and keeps the lock until its database unit has ended even if the unlinking task is cancelled meanwhile (`WebDatabase.run_to_completion`); an unlink that finds no link only withdraws the pairing codes and removes nothing, so a link made after it looked is never cut; queued work whose tie is gone is dropped, never redirected. This is not exactly-once delivery of anything that leaves the process: an answer already generated can reach Telegram twice, an acknowledged message in flight when the process is killed gets no answer, and the operator's `revoke`/`disable` (another process) cannot take the in-process lock. | ACCEPTED — owner (remediation briefs for the review findings, 2026-10-28, REPORTED; second round: three reproduced blockers); independent final verdict PASS and owner ACCEPT of the implementation and security remediation, 2026-10-28, REPORTED; code released in the repository, **not deployed** |

### Why / alternatives / boundaries

- **Polling inside the Web process vs a webhook or a separate bot process:** a second process would be a second writer on SQLite and would have to reimplement the turn lifecycle; a webhook needs a public route, a secret and a `setWebhook` call, and cannot coexist with polling on one token. In-process polling needs none of these and goes through code that is already tested. The price is the one-consumer, one-instance condition above, which is why a conflict is made visible instead of silently ignored.
- **A minimal signal, not a monitoring system:** the start-up poll waits for nothing, so a refused token or a second consumer shows within a second; the state is one field (`TelegramChat.failure`) read by the pairing routes; the log has one line for the start, one `ERROR` for a blocked or refused bot and one for the recovery. `/healthz` stays a liveness check of the process. Whether the separate monitoring work stream watches those lines is not decided here (the lines are listed in `deploy/RUNBOOK.md` 16.5).
- **Mirroring by default, no toggle:** the owner chose the simple behaviour and accepted that unlinking is the only way to stop it; the cost of a toggle (state, UI, tests, a second meaning of "linked") was not wanted for two users.
- **Web upload deferred:** it adds an upload endpoint, a file input, client-side limits and a second abuse surface; the Telegram path already exercises storage, validation, display and retention.
- **Redelivery and ties (KHD-38):** the owner chose to fix the two findings without redesigning the integration. The assistant is protected by what the database already records (the claim is committed before the provider is called), a delivery-time check and a lock are enough for the two-person alpha, and neither a queue nor a persisted polling offset is introduced. The alternative of persisting the offset was rejected: it would not stop a redelivery caused by a lost acknowledgement, and it would add state. In the second round the cross-owner finding was closed without a table: the claim's turn request is already written in the same transaction as the admission, so reading it across owners (and holding the link while doing so) is atomic with the claim; a table of update ids would add a migration, a retention rule and an upgrade step for no stronger guarantee. The price is a scan of `turn_requests` by key (small: two people, 365 days); an index on the key is the remedy if that ever matters, as a decision of its own.
- **Not decided here:** more than one Web instance or more than one reader of the token (that needs a webhook or a queue, a new decision); groups, voice, documents sent as files, albums grouped into one message; a per-user mirroring toggle; Web photo upload; whether the monitoring watches the new log lines.
