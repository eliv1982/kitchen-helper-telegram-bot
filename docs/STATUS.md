What A3 released (all in Git; behavior only in tests and local stands):

- **Migration `0006_oidc_state_invitation`** (revision chain `0005_identity_invitations` → `0006`): one empty nullable column `oidc_states.invitation_id` (foreign key to `identity_invitations`, `ON DELETE CASCADE`) plus an index; existing rows stay ordinary logins, sessions are not revoked; downgrade first deletes invitation-bound login states so they cannot become ordinary ones. **Not applied to any real or production database.**
- **Secure invitation Web page and start endpoint:** `GET /auth/invite` (Russian page, identical for everyone, spends and writes nothing), `POST /auth/invite/start` (JSON `{"code": ...}` only) and `GET /auth/invite/done`. The invitation secret travels in the URL fragment, which the browser never sends to the server; the page's single hashed inline script removes the fragment from the address bar and history, keeps the code in memory only and sends it in one same-origin `POST` body when the person presses the button. If the fragment cannot be removed the page closes itself (button disabled, code erased, nothing sent). Every unusable-invitation reason gets the same `400 invitation_invalid`.
- **Server-side binding of the verified invitation to the OIDC state:** the invitation id is stored in the `oidc_states` row of the login that was started after the secret was verified, and on return from Telegram it is read only from that consumed row — never from a query parameter, cookie or body.
- **Browser-bound OIDC flow with the existing PKCE and nonce verification:** the login cookie, PKCE, `nonce` and the ID-token signature/`iss`/`aud` checks are the R3A ones, unchanged; the callback route and redirect URI are the ordinary ones (one address in BotFather).
- **Atomic invitation consumption, identity linking and session issuance:** in one write transaction the invitation is consumed, the verified `sub` is stored in that user's allowlist, the identity link is created and the session is issued (14 days); afterwards the session is asserted to belong to the invited user. Any failure rolls everything back, the invitation stays valid. `sub` is taken only from the verified token; an already-used or revoked `sub` is never adopted or revived.
- **Two independent `User` identities and conversation isolation:** each of the two people links their own Telegram identity to their own `User`; every conversation still belongs to the user of the session, and no chat or conversation code was changed.
- **Ordinary Telegram login after initial linking, including from another device:** once linked, the person signs in with the ordinary "Войти через Telegram" button — no invitation is needed — and the same code cannot be used twice.
- **Rejection of ordinary cross-user login conflicts without replacing the existing session cookie:** a return from Telegram in a browser that holds a live session of a *different* user (ordinary login and invitation login alike) answers `409 signed_in_as_another_user` (a Russian page, no names or identifiers), compared inside the same transaction that would issue the session; the existing session and cookie are left as they were and nothing is written. The same user signing in again is unaffected. Known limit (pinned by a test): a cookie the browser had not yet sent when a parallel tab signed in is invisible to this check.
- **Russian-language invitation, success, failure and conflict pages** with fixed wording that carries no `sub`, name, user or invitation identifier and no failure reason.
- **The existing 14-day absolute session policy is unchanged** (KHD-11).

## Existing vs not yet built

- **Released in Git (reported):** persistence schema, FastAPI service foundation, Telegram OIDC, per-identity session provenance/revocation, passwordless email login.
- **Released in Git (R3B-3):** operator CLI `python -m house_helper.admin provision-email` (`house_helper/admin/`): creates the first `User` and its approved email allowlist entry in one transaction, email-first; refuses when a user already exists, never creates a Telegram identity, never applies migrations. Offline tests run on SQLite; the optional real-PostgreSQL suite (`tests/test_admin_postgres.py`) skips unless `HOUSE_HELPER_TEST_POSTGRES_URL` is set and is not run by CI. Details: root `README.md`, section "Первый пользователь".
- **Released in Git (R4A):** authenticated, persistent Web Chat API (`house_helper/web/chat_api.py`, `turn_runner.py`, `diagnostics.py`; `house_helper/persistence/conversations.py` and the `begin_turn`/`complete_turn`/`fail_turn` lifecycle in `turns.py`; standalone OpenAI backend `house_helper/core/openai_chat.py`): create/list conversations, read history, send a message under an `Idempotency-Key`. One turn at a time per conversation, lease-fenced turn recovery, model call outside DB transactions, 365-day `expires_at` recorded on stored messages. **No schema change and no migration** (`0001`–`0004` unchanged). The Telegram bot's behavior is unchanged apart from the shared system prompt and the default `MAX_TOKENS` 600 → 1000 (an existing `.env` value is kept). Details: root `README.md`, section "Веб-чат (API)".
- **Released in Git (R4B), as a local Web alpha only:** the Russian-language responsive page "Кухонный помощник" on top of the R4A API (`house_helper/web/ui.py`: the server-made shell at `GET /` and a whitelist of `GET /static/{app.js, chat-logic.js, app.css, icon.svg}`; plain HTML/CSS/JavaScript, no build step, no external scripts or CDN, no new dependency). It shows only the sign-in methods that are configured, lists and continues several conversations (a new one is created by its first message), loads older messages, and sends each message under its own idempotency key. An unclear outcome (any `5xx` included) is never treated as a verdict: the only action is a retry with the same key and text, and the message can be taken back only when the server definitely refused it. Sending waits for the conversation's history; the session deadline and the signed-in user are re-checked when a tab comes back; signing out clears the conversation at once. Text is drawn as text only (strict CSP, no `innerHTML`). **Two backend changes:** (1) `POST /auth/logout` now requires a single `X-Expected-User` header (the `user_id` from `/auth/me`) and ends the cookie's session only if it is that user's (`409 session_mismatch` for another user's session, `400 invalid_request` for a missing or invalid header; `persistence.authn.revoke_session_of`); (2) the redirect after a successful sign-in is `/` instead of `/auth/me`. **No schema change, no migration, no dependency change** (`0001`–`0004` unchanged). Details: root `README.md`, section "Веб-интерфейс (кухня)".
- **Owner-accepted R4B residuals (REPORTED, accepted for this milestone):** an explicit sign-out discards an unresolved message record by design; unresolved records older than 6 hours are dropped (the page says so); a sign-in by email link in another tab does not see the first tab's record; a device clock error shifts the local sign-out by that error; the reader's scroll position is not kept when a tab comes back; the logout guard is per user, not per session, and a repeated logout by the same user clears the cookie by name even if someone else signed in while it was in flight; the server session can outlive a mismatched logout (it expires on its own after 14 days); an old page loaded before the update gets `400` on logout until it is reloaded.
- **Released in Git (R4C-Auth A2), operator side only:** closed, operator-controlled enrollment of two independent internal users through Telegram invitations. Migration `0005_identity_invitations` (revision chain `0004_email_identity_case` → `0005`; creates only the new `identity_invitations` table, `0001`–`0004` unchanged), `house_helper/persistence/invitations.py`, `house_helper/admin/enrollment.py` and four operator commands under `python -m house_helper.admin`: `enroll-user`, `reissue-invitation`, `revoke-invitation`, `enrollment-status`. Only the operator creates users (no self-registration), and a user's Telegram allowlist entry appears only when an invitation is claimed. An invitation is Telegram-only, valid for two hours, single use and revocable; one outstanding invitation per user (a reissue revokes the previous one); only the SHA-256 of its secret is stored, and the code is printed once. **The limit of two users is a temporary policy of the `enroll-user` command, not a database restriction** — the schema has no such constraint, and the command counts users inside its own transaction at creation only. Concurrency is serialized with the same advisory lock as `provision-email` on PostgreSQL (write-first on SQLite) plus a fixed user-row-then-invitation-row lock order; claiming an invitation persists the consumed invitation and the verified `sub` in the user's allowlist in one atomic transaction and refuses an already-provisioned identity. **Existing conversation ownership and isolation are unchanged:** every conversation still belongs to the user of the session, and no Web route, session, chat or conversation code was changed. After a second user exists `provision-email` keeps refusing (`multiple_users`), unchanged behavior. Details: root `README.md`, section "Начальные пользователи: приглашения Telegram".
- **Released in Git (R4C-Auth A3), code only — not deployed:** the Web side of the invitation: migration `0006_oidc_state_invitation` (`oidc_states.invitation_id`; `0001`–`0005` unchanged), `GET /auth/invite`, `POST /auth/invite/start`, `GET /auth/invite/done`, the invitation branch of the ordinary `GET /auth/telegram/callback`, Russian invitation/success/failure/conflict pages (`house_helper/web/invite_auth.py`, `invite_pages.py`, `auth.py`; `house_helper/persistence/invitations.py`, `authn.py`), and a `409 signed_in_as_another_user` for any Telegram return in a browser signed in as a different user.
