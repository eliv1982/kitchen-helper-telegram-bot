What A3 released (all in Git; behavior only in tests and local stands):

- **Migration `0006_oidc_state_invitation`** (revision chain `0005_identity_invitations` → `0006`): one empty nullable column `oidc_states.invitation_id` (foreign key to `identity_invitations`, `ON DELETE CASCADE`) plus an index; existing rows stay ordinary logins, sessions are not revoked; downgrade first deletes invitation-bound login states so they cannot become ordinary ones. **Not applied to any real or production database.**
- **Secure invitation Web page and start endpoint:** `GET /auth/invite` (Russian page, identical for everyone, spends and writes nothing), `POST /auth/invite/start` (JSON `{"code": ...}` only) and `GET /auth/invite/done`. The invitation secret travels in the URL fragment, which the browser never sends to the server; the page's single hashed inline script removes the fragment from the address bar and history, keeps the code in memory only and sends it in one same-origin `POST` body when the person presses the button. If the fragment cannot be removed the page closes itself (button disabled, code erased, nothing sent). Every unusable-invitation reason gets the same `400 invitation_invalid`.
- **Server-side binding of the verified invitation to the OIDC state:** the invitation id is stored in the `oidc_states` row of the login that was started after the secret was verified, and on return from Telegram it is read only from that consumed row — never from a query parameter, cookie or body.
- **Browser-bound OIDC flow with the existing PKCE and nonce verification:** the login cookie, PKCE, `nonce` and the ID-token signature/`iss`/`aud` checks are the R3A ones, unchanged; the callback route and redirect URI are the ordinary ones (one address in BotFather).
- **Atomic invitation consumption, identity linking and session issuance:** in one write transaction the invitation is consumed, the verified `sub` is stored in that user's allowlist, the identity link is created and the session is issued (14 days); afterwards the session is asserted to belong to the invited user. Any failure rolls everything back, the invitation stays valid. `sub` is taken only from the verified token; an already-used or revoked `sub` is never adopted or revived.
- **Two independent `User` identities and conversation isolation:** each of the two people links their own Telegram identity to their own `User`; every conversation still belongs to the user of the session, and no chat or conversation code was changed.
- **Ordinary Telegram login after initial linking, including from another device:** once linked, the person signs in with the ordinary "Войти через Telegram" button — no invitation is needed — and the same code cannot be used twice.
- **Rejection of ordinary cross-user login conflicts without replacing the existing session cookie:** a return from Telegram in a browser that holds a live session of a *different* user (ordinary login and invitation login alike) answers `409 signed_in_as_another_user` (a Russian page, no names or identifiers), compared inside the same transaction that would issue the session; the existing session and cookie are left as they were and nothing is written. The same user signing in again is unaffected. Known limit (pinned by a test): a cookie the browser had not yet sent when a parallel tab signed in is invisible to this check.
