## Existing vs not yet built

- **Released in Git (reported):** persistence schema, FastAPI service foundation, Telegram OIDC, per-identity session provenance/revocation, passwordless email login.
- **Released in Git (R3B-3):** operator CLI `python -m house_helper.admin provision-email` (`house_helper/admin/`): creates the first `User` and its approved email allowlist entry in one transaction, email-first; refuses when a user already exists, never creates a Telegram identity, never applies migrations. Offline tests run on SQLite; the optional real-PostgreSQL suite (`tests/test_admin_postgres.py`) skips unless `HOUSE_HELPER_TEST_POSTGRES_URL` is set and is not run by CI. Details: root `README.md`, section "Первый пользователь".
- **Released in Git (R4A):** authenticated, persistent Web Chat API (`house_helper/web/chat_api.py`, `turn_runner.py`, `diagnostics.py`; `house_helper/persistence/conversations.py` and the `begin_turn`/`complete_turn`/`fail_turn` lifecycle in `turns.py`; standalone OpenAI backend `house_helper/core/openai_chat.py`): create/list conversations, read history, send a message under an `Idempotency-Key`. One turn at a time per conversation, lease-fenced turn recovery, model call outside DB transactions, 365-day `expires_at` recorded on stored messages. **No schema change and no migration** (`0001`–`0004` unchanged). The Telegram bot's behavior is unchanged apart from the shared system prompt and the default `MAX_TOKENS` 600 → 1000 (an existing `.env` value is kept). Details: root `README.md`, section "Веб-чат (API)".
- **Released in Git (R4B), as a local Web alpha only:** the Russian-language responsive page "Кухонный помощник" on top of the R4A API (`house_helper/web/ui.py`: the server-made shell at `GET /` and a whitelist of `GET /static/{app.js, chat-logic.js, app.css, icon.svg}`; plain HTML/CSS/JavaScript, no build step, no external scripts or CDN, no new dependency). It shows only the sign-in methods that are configured, lists and continues several conversations (a new one is created by its first message), loads older messages, and sends each message under its own idempotency key. An unclear outcome (any `5xx` included) is never treated as a verdict: the only action is a retry with the same key and text, and the message can be taken back only when the server definitely refused it. Sending waits for the conversation's history; the session deadline and the signed-in user are re-checked when a tab comes back; signing out clears the conversation at once. Text is drawn as text only (strict CSP, no `innerHTML`). **Two backend changes:** (1) `POST /auth/logout` now requires a single `X-Expected-User` header (the `user_id` from `/auth/me`) and ends the cookie's session only if it is that user's (`409 session_mismatch` for another user's session, `400 invalid_request` for a missing or invalid header; `persistence.authn.revoke_session_of`); (2) the redirect after a successful sign-in is `/` instead of `/auth/me`. **No schema change, no migration, no dependency change** (`0001`–`0004` unchanged). Details: root `README.md`, section "Веб-интерфейс (кухня)".
- **Owner-accepted R4B residuals (REPORTED, accepted for this milestone):** an explicit sign-out discards an unresolved message record by design; unresolved records older than 6 hours are dropped (the page says so); a sign-in by email link in another tab does not see the first tab's record; a device clock error shifts the local sign-out by that error; the reader's scroll position is not kept when a tab comes back; the logout guard is per user, not per session, and a repeated logout by the same user clears the cookie by name even if someone else signed in while it was in flight; the server session can outlive a mismatched logout (it expires on its own after 14 days); an old page loaded before the update gets `400` on logout until it is reloaded.
- **Not verified in a real environment:** BotFather/OIDC flow; real SMTP delivery; magic-link browser E2E; final reverse proxy/cookie topology; `provision-email` against any real (production) database; the Web Chat API against the real OpenAI API (no real provider call has been made; prompt quality, redirects and distress wording are unevaluated); the Web Chat HTTP layer on real PostgreSQL (persistence and runner were run on PostgreSQL 16 through the opt-in suite, not through HTTP); the R4B page in any browser other than headless Chrome 155 on Windows (REPORTED: exercised there against a local scratch stand with a fake assistant and mailer, outside the repository) — not Edge, Firefox, Safari, a real phone, a screen reader or an IME, and the guarded-logout `409` path was covered by the Python and Node tests but not re-run in a real browser.
- **Not yet implemented as user-facing Web product:** history page, favorites UI, preferences UI, STT/TTS; also conversation titles (the page labels a conversation by its date), deleting or resetting a conversation, response streaming, per-user rate limits. (The responsive chat page itself exists as the R4B local alpha.)
- **Not implemented (decided or proposed only):** Telegram initial linking (verified `sub` acquisition); House Helper domain selection and non-Kitchen domains (KHD-15–KHD-19); n8n error monitoring and correlation IDs (KHD-20, KHD-22); the Web UI palette (KHD-21).

## Deployment gates / known risks

- **R4B local alpha → first-user beta (all gates outstanding, none attempted):** real SMTP delivery (with TLS, SPF/DKIM/DMARC) and real Telegram login (BotFather/OIDC, plus the unbuilt initial `sub` linking); a real OpenAI call and a review of answer quality (provider gate below); applying migrations `0002`–`0004` to a real database; the physical retention purge and the public-ingress protection (both below); a public HTTPS address (a phone can use the page only over `https`; plain `http` works for localhost only); real-device and cross-browser checks (a real phone, Safari, Edge, Firefox, a screen reader, an IME). Each needs explicit owner authorization.
- Existing DB migrations `0002`–`0004` not applied as of handoff: require explicit authorization, stop/backup/upgrade/integrity/restart/re-login procedure.
- `provision-email` has not been run against any real database; no real user is provisioned. Run it only after the migrations are applied and finished: migrations and `provision-email` must never run concurrently (an operational rule, not enforced by code). Real provisioning needs explicit owner authorization.
- **Physical retention purge (R4A gate):** messages and turn requests carry a 365-day `expires_at` and expired rows are hidden from reads and model context, but **nothing deletes them yet**. A purge job (or an owner-approved equivalent) must exist before real user data is stored.
- **Public ingress security (R4A gate):** the Web Chat API has no global provider-concurrency cap, per-user or per-IP rate limit, or conversation count limit; these belong to the trusted ingress/reverse proxy and are not built or verified. Required before any public exposure, together with the existing auth-endpoint rate limits below.
- **Real-provider evaluation (R4A gate):** run the chat against the real OpenAI API with the owner's authorization and review answer quality and `truncated` behavior before real use; the shared system prompt and the 1000-token default have never met a real model in this project's tests.
- Timing differentiation in email login request path (reported approx. 4.14 ms approved vs 1.94 ms unknown) needs production mitigation with request throttling.
- Rate limit auth endpoints at trusted ingress; filter secret-bearing callback query strings at all logging layers; verify SMTP SPF/DKIM/DMARC, TLS and browser cookies.
- No arbitrary migration, deployment, account merging or re-enabling revoked legacy email without owner approval and independent verification.
- GitHub Actions Node 20 warnings and Ubuntu runner transition are maintenance items, not automatic scope expansions; act on real failures or approved cleanup.
